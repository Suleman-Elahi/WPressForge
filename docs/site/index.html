The open-source WordPress manager for your own servers.

WPressForge is a self-hosted alternative to RunCloud, GridPane and EasyEngine. A small Rust control plane drives a privileged agent on each node, which provisions Docker, Nginx, MariaDB, TLS, backups and WP-CLI for you — with no per-site licence and no vendor holding your credentials.

How it works

Two roles, one contract, no shell strings

The panel never logs into your servers. It describes what should happen as a typed operation; the agent decides how, on the node where it actually runs.

Everything is a job

Site creation, PHP switches, backups and certificate issuance are rows in a jobs table. Workers execute them and report each step back live. Interrupted jobs are marked failed on restart instead of silently vanishing.

The panel has no privileges

It never runs a shell command on a node, and it holds no root. Compromising the UI does not hand over your fleet; the agent validates every request independently.

The agent builds argument vectors

Operations are defined in a shared protocol crate. The agent assembles argv arrays — never shell strings — and whitelists the WP-CLI subcommands it will run.

Agents are pinned, not trusted

Each node is reached over TLS with its certificate fingerprint pinned, plus a bearer token. The panel refuses an unpinned HTTPS agent, and refuses plain HTTP off loopback.

Feature set

What you actually get

The day-to-day work of running WordPress — provisioning, updates, backups, staging and access — without a proprietary panel in the middle.

Multi-server sites

Sites, domains, caches and resource limits per site, with every node under one dashboard. Add a node and it becomes a deployment target immediately.

Zero-downtime PHP switches

New container up, health-checked, Nginx upstream moved, traffic verified, then the old container removed. Per-site PHP 8.2 / 8.3 / 8.4.

Per-site isolation

Dedicated Linux UID, one PHP-FPM container with CPU, memory and PID limits, cap-drop ALL, read-only rootfs, and a private or dedicated database.

Encrypted, scheduled backups

Restic snapshots straight from the node to any S3-compatible store — AWS, R2, B2, Wasabi, MinIO — with retention policies and one-click restore.

Clone, staging and push

Spin up staging.example.com from production, work on it, then push back — which takes a safety backup first and is refused if it would hit the wrong target.

WordPress management

Plugins, themes, users and cron jobs, plus a constrained WP-CLI console that whitelists subcommands instead of handing over a shell.

Metrics, logs and alerting

CPU, memory and disk history with inline sparklines, per-site log viewing, and threshold alerts delivered in-app or by SMTP.

Import existing sites

Point it at a server over SSH and it inspects, then migrates, an existing WordPress install — searching and replacing the old URL as it goes.

Teams and roles

Invitations, roles and per-site grants, so a client can reach exactly one site and a viewer cannot mutate anything.

Security foundations

CSRF protection, TLS-pinned agents, API tokens, login throttling and TOTP two-factor authentication — on by default, not a paid tier.

JSON API

An authenticated /api/v1 scoped to the caller's own sites and servers, for automation and pipelines.

Adapts to the host

The agent probes nginx -V at startup and renders only directives the installed binary understands — http2 on; vs the listen parameter, HTTP/3 only where compiled in, brotli otherwise gzip_static.

Isolation

One site cannot touch another

Each site gets its own Linux identity and its own container. The container is limited, stripped of capabilities and has a read-only root filesystem — with only that site's directories bind-mounted in.

  • Dedicated UID per site, allocated above 10001
  • CPU, memory and PID caps enforced per container
  • cap-drop ALL and no-new-privileges
  • Read-only rootfs with a small noexec tmpfs
  • Private schema or a dedicated MariaDB container
  • Redacted logs — passwords never reach the journal

Comparison

How it compares to the panels you already know

WPressForge targets one specific job: managing WordPress on hardware you already pay for. That puts it beside the server-management panels and the open-source CLI tools — not the managed hosts, which solve a different problem entirely.

Summarised in good faith as of 2026. All three columns are aiming at the same job, and the commercial panels are mature products whose real feature sets run deeper than any table can show. EasyEngine's open-source CLI in particular is excellent at what it does — the difference is that it stops at the command line, on one server. Managed hosts such as Kinsta, WP Engine and Cloudways are a different category: if you would rather not own the servers at all, they will always be the better trade.

Where the project actually stands

All planned milestones are implemented and verified — auth with CSRF, TLS-pinned agents, API tokens, throttling and TOTP; sites, domains, cache and limits; WordPress management, backups, clone and staging, import, metrics and alerting; teams with roles and per-site grants. Quality gates are cargo fmt --check, clippy -D warnings with no suppressions, and 97 passing tests.

  • Proven: node operations exercised with WP_AGENT_DRY_RUN=true — every command logged, nothing executed — plus real nginx -t validation of both generated dialect variants.
  • Not yet proven: the first run against live Docker, MariaDB and certbot still needs a shakedown, and the full site-import path needs two hosts to demonstrate end to end.
  • Practical advice: do your first site on a throwaway node, with console access, before moving real workloads across.
Get started

Two commands to a running panel

Run the panel with demo data on 127.0.0.1:8080 to explore the interface, and a dry-run agent alongside it that logs commands instead of executing them. Nothing on the host is touched until you say so.

Read the README Deployment guide Runbook 
# Panel with demo data
WP_PANEL_ADMIN_PASSWORD=devpassword \
  cargo run -p wp-panel

# Dry-run agent: logs commands, touches nothing
WP_AGENT_TOKEN=local-development-token-000001 \
WP_AGENT_BIND=127.0.0.1:8443 \
WP_AGENT_STATE=data/agent-state.json \
  cargo run -p wp-agent
